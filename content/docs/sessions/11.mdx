## 앱의 세 가지 모양

"앱을 만들고 싶어요"라고 말할 때 사람들이 떠올리는 것은 사실 세 가지 중 하나입니다.

| 모양 | 어떻게 여나 | 어디서 받나 | 예시 |
| --- | --- | --- | --- |
| <Term id="web-app">웹앱</Term> | 브라우저에 주소 입력, 링크 누르기 | 받을 필요 없음 | 지금까지 만든 우리 모임 웹앱 |
| <Term id="pwa">PWA</Term> | 홈 화면 아이콘 누르기 | 웹사이트에서 "홈 화면에 추가" | 홈 화면에 설치한 우리 모임 |
| <Term id="native-app">네이티브 앱</Term> | 홈 화면 아이콘 누르기 | 앱스토어, 구글 플레이 | 카카오톡, 은행 앱 |

<Analogy title="가게에 비유하면">
  **웹앱**은 길가의 가게입니다. 누구나 주소만 알면 들어올 수 있고, 간판을 바꾸면 바로 모두에게 보입니다. **PWA**는 그 가게의 단골 카드입니다. 지갑(홈 화면)에 넣어 두고 꺼내기만 하면 바로 가게로 연결됩니다. **네이티브 앱**은 백화점(앱스토어)에 입점한 매장입니다. 입점 심사를 받고 수수료를 내야 하지만, 백화점이 가진 시설(알림, 카메라, 결제 등)을 깊게 쓸 수 있고 사람들이 찾아오기도 쉽습니다.
</Analogy>

### 웹앱: 이미 가진 것

- 지금 우리가 가진 것입니다. 링크 하나로 열리고, 컴퓨터와 휴대폰 모두에서 됩니다.
- 고치면 **배포하는 순간 모두에게 바로 반영**됩니다(6회에서 체험했습니다).
- 단점: 휴대폰에서 매번 브라우저를 열어야 하고, 주소창과 메뉴가 화면을 차지합니다. 휴대폰 기능(알림, 잠금 화면 위젯 등)을 쓰는 데 제약이 있습니다.

### PWA: 웹앱에 "설치" 기능을 더한 것

PWA는 Progressive Web App의 줄임말입니다. 이름은 어렵지만 하는 일은 간단합니다. **웹앱에 "나를 앱처럼 설치할 수 있어요"라는 신분증을 붙이는 것**입니다.

- 이 신분증이 <Term id="manifest">웹 앱 매니페스트</Term>라는 작은 파일입니다. 앱 이름, 아이콘, 시작 화면 색, 주소창을 숨길지 등을 적어 둡니다.
- 설치하면 홈 화면에 아이콘이 생기고, 누르면 **주소창 없이 앱처럼 꽉 찬 화면**으로 열립니다.
- 속은 여전히 웹앱이라 **배포하면 바로 반영**되고, 스토어 심사도 등록비도 없습니다.

### 네이티브 앱: 스토어에 올리는 앱

- 안드로이드와 아이폰이 각각 알아듣는 방식으로 만든 앱입니다. 원래는 안드로이드용과 아이폰용을 따로 만들어야 했습니다.
- 휴대폰 기능을 가장 깊게 씁니다. 푸시 알림, 카메라, 위치, 걸음 수, 블루투스, 위젯 등.
- 스토어에 올리려면 등록비와 심사가 필요합니다. 애플은 <Fact k="apple.dev" />, 구글은 <Fact k="google.dev" />입니다.
- 고친 것을 내보내려면 원칙적으로 새로 빌드해서 다시 심사를 받아야 합니다(14회에서 예외인 OTA 업데이트를 배웁니다).

## 무엇으로 시작할까: 고르는 기준

정답은 "만들고 싶은 것"이 아니라 "**꼭 필요한 기능**"이 정합니다.

| 질문 | 예라면 | 아니라면 |
| --- | --- | --- |
| 회원이 휴대폰 홈 화면에서 바로 열면 좋은가? | PWA 이상 | 웹앱으로 충분 |
| 휴대폰 기능을 깊게 써야 하나? (걸음 수, 블루투스, 정교한 알림) | 네이티브 앱 | PWA로 충분 |
| 앱스토어·플레이스토어에서 검색되어야 하나? | 네이티브 앱 | PWA로 충분 |
| 일주일 안에 회원들에게 내놓아야 하나? | 웹앱·PWA | 네이티브도 가능 |
| 등록비와 심사 기간을 감당할 수 있나? | 네이티브도 가능 | 웹앱·PWA |

<Analogy title="이사보다 리모델링부터">
  지금 집(웹앱)이 멀쩡한데 새 집(네이티브 앱)을 짓기 전에, 먼저 현관에 문패(PWA)부터 다는 것과 같습니다. 대부분의 작은 서비스는 PWA만으로도 "앱처럼 쓴다"는 목표를 이룹니다. 써 보니 부족한 점이 분명해졌을 때 네이티브 앱으로 가면, 무엇이 필요한지 정확히 알고 시작할 수 있습니다.
</Analogy>

우리 모임 서비스에 적용해 보면 다음과 같습니다.

| 기능 | 웹앱 | PWA | 네이티브 앱 |
| --- | --- | --- | --- |
| 모임 일정 보기, 참석 신청 | 됨 | 됨 | 됨 |
| 홈 화면 아이콘 | 안 됨 | 됨 | 됨 |
| 주소창 없는 꽉 찬 화면 | 안 됨 | 됨 | 됨 |
| 모임 전날 알림 | 제약 많음 | 휴대폰·브라우저에 따라 다름 | 됨 |
| 스토어 검색 | 안 됨 | 안 됨 | 됨 |
| 고친 것 반영 | 배포 즉시 | 배포 즉시 | 새 빌드(또는 OTA 업데이트) |

그래서 이 과정은 **오늘 PWA로 먼저 홈 화면에 올리고**, 12–14회에 같은 데이터를 쓰는 네이티브 앱을 Expo로 만들어 출시 준비까지 해 봅니다. 두 길을 다 가 보면 다음에 무엇을 고를지 스스로 판단할 수 있습니다.

<PromptCard id="pwa-or-native" />

<DeepDive title="PWA는 아이폰과 안드로이드에서 다르게 설치됩니다">

웹 개발 공식 학습 사이트인 [web.dev의 PWA 설치 안내](https://web.dev/learn/pwa/installation)에 따르면 두 휴대폰은 방식이 다릅니다.

- **안드로이드(크롬):** 크롬이 PWA를 진짜 앱에 가깝게 설치합니다. 메뉴에 "앱 설치" 또는 "홈 화면에 추가"가 보이고, 설치하면 앱 목록에도 아이콘이 생깁니다. 조건이 맞지 않으면 단순한 바로가기로 만들어집니다.
- **아이폰(사파리):** 설치 안내 창이 자동으로 뜨지 않습니다. 사용자가 직접 **공유 버튼 → 홈 화면에 추가**를 눌러야 합니다. 그래서 회원들에게 "이렇게 누르세요"라는 안내가 꼭 필요합니다.
- 아이폰은 아이콘 이미지를 따로 지정하지 않으면 화면을 찍은 사진이 아이콘이 됩니다. 그래서 아이콘 파일을 꼭 넣어 둡니다.

이런 차이는 휴대폰 운영체제와 브라우저가 업데이트되면서 계속 바뀝니다. 실제 회원에게 안내하기 전에는 **내 휴대폰에서 직접 해 보는 것**이 가장 확실합니다.

</DeepDive>

### 휴대폰 화면은 컴퓨터 화면과 다릅니다

PWA로 설치하면 회원들은 이 서비스를 "앱"으로 느낍니다. 그러면 기대도 앱 수준으로 올라갑니다. 휴대폰에서 쓰기 편한지 세 가지만 기억하세요.

| 원칙 | 왜 | 이렇게 |
| --- | --- | --- |
| **손가락 크기** | 마우스보다 손가락이 훨씬 굵습니다 | 버튼은 크게, 버튼 사이는 넉넉하게 |
| **엄지가 닿는 곳** | 한 손으로 쓰는 경우가 많습니다 | 자주 누르는 버튼(참석 신청)은 화면 아래쪽 |
| **읽기 쉬운 글자** | 작은 화면, 다양한 나이의 회원 | 본문 글자를 충분히 크게, 대비는 진하게 |

## 요즘 업계에서는

### "하나로 만들어 여러 곳에" — 크로스 플랫폼

예전에는 웹, 안드로이드, 아이폰을 각각 다른 언어로, 다른 팀이 만들었습니다. 요즘은 **한 번 만들어 여러 곳에 내보내는** <Term id="cross-platform">크로스 플랫폼</Term> 방식이 흔해졌습니다.

- 다음 시간에 쓸 <Term id="react-native">React Native</Term>는 웹에서 쓰던 React 방식 그대로 안드로이드와 아이폰 앱을 만듭니다. React Native 공식 문서는 새 앱을 시작할 때 **Expo 같은 프레임워크를 쓰라고 권합니다** ([React Native 시작하기](https://reactnative.dev/docs/environment-setup)).
- 4회에 배운 Next.js도, 12회에 쓸 Expo도 둘 다 React를 씁니다. 그래서 **웹앱을 만들어 본 경험이 앱으로 그대로 이어집니다.** Claude Code도 두 쪽을 다 잘 다룹니다.

### "웹 먼저, 앱은 나중에"

새 서비스를 시작할 때 웹이나 PWA로 먼저 내놓고, 쓰는 사람이 늘고 필요한 기능이 분명해지면 스토어 앱을 만드는 흐름이 많습니다. 이유는 간단합니다.

- 웹은 고치면 바로 반영됩니다. 처음에는 하루에도 몇 번씩 고치게 되는데, 그때마다 스토어 심사를 기다릴 수는 없습니다.
- 써 보기 전에는 무엇이 필요한지 모릅니다. 2회에 배운 <Term id="mvp">MVP</Term>(꼭 필요한 것만 넣은 첫 버전)의 생각과 같습니다.

### AI가 바꾼 계산

1회에 소개한 [a16z의 "일회용 소프트웨어(Disposable Software)"](https://a16z.com/disposable-software/) 이야기를 기억하시나요? 만드는 비용이 크게 줄면서, 작은 모임을 위한 작은 앱처럼 **예전에는 만들 엄두를 못 내던 것**도 만들어 볼 만해졌습니다. 그렇다고 모든 것을 스토어 앱으로 만들 필요는 없습니다. **만드는 비용이 줄수록 "무엇으로 만들지 고르는 판단"이 더 중요해집니다.** 오늘 표로 정리한 기준이 그 판단입니다.

<Callout title="Vercel은 웹을, Expo는 앱을">
  6회에 쓴 Vercel은 웹사이트와 서버를 올리는 곳입니다. 휴대폰에 설치하는 네이티브 앱 파일을 Vercel이 만들어 주지는 않습니다. 네이티브 앱은 12–14회에 Expo로 만들고, 웹과 앱이 같은 Supabase 데이터를 함께 씁니다. PWA는 웹앱이므로 지금처럼 Vercel에 그대로 배포하면 됩니다.
</Callout>

## 시연

강사가 우리 모임 웹앱을 Claude Code로 PWA로 바꿉니다. 아이콘과 앱 이름("책 읽는 저녁")을 정하고, GitHub에 푸시해 Vercel에 배포한 뒤, 안드로이드 휴대폰과 아이폰에서 각각 홈 화면에 설치합니다. 설치 전(브라우저 주소창이 보이는 화면)과 설치 후(꽉 찬 화면)를 나란히 비교하고, 비행기 모드를 켜서 인터넷이 끊겼을 때 어떻게 보이는지도 확인합니다.
