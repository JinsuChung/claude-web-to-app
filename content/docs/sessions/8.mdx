## 지금 웹앱의 문제

7회까지 만든 웹앱은 이런 상태입니다.

- 누구나 모임을 만들 수 있습니다. 장난으로 모임을 100개 만들어도 막을 방법이 없습니다.
- 누구나 남의 모임을 고치거나 지울 수 있습니다.
- 공개 키는 화면 코드에 실려 있어 **누구나 볼 수 있습니다.** 마음만 먹으면 웹앱을 거치지 않고 데이터베이스에 직접 요청을 보낼 수도 있습니다.

<Analogy title="열쇠가 꽂혀 있는 공용 사물함">
  지금은 동네 사물함마다 열쇠가 꽂혀 있는 상태입니다. 착한 이웃만 있다면 괜찮지만, 주소가 공개된 웹에서는 그렇게 기대할 수 없습니다. 오늘은 **이름표(로그인)** 를 달고, **내 이름표가 붙은 칸만 열리는 자물쇠(RLS)** 를 채웁니다.
</Analogy>

## 인증과 권한은 다릅니다

보안 이야기에서 가장 먼저 구분해야 할 두 단어가 있습니다.

| | <Term id="auth">인증</Term> (Authentication) | <Term id="authorization">권한</Term> (Authorization) |
| --- | --- | --- |
| 묻는 질문 | 당신은 **누구**인가요? | 당신은 **무엇을** 할 수 있나요? |
| 일상의 예 | 회사 출입증 찍기 | 출입증으로 들어갈 수 있는 층 |
| 우리 웹앱 | 이메일과 비밀번호로 로그인 | 내가 만든 모임만 고치기 |
| 담당 | Supabase Auth | RLS 보안 규칙 |

**로그인만 붙이고 권한을 정하지 않으면** 반쪽짜리 보안입니다. "누구인지는 아는데 아무거나 다 할 수 있는" 상태가 되기 때문입니다. 실제 사고는 대부분 이 두 번째를 빠뜨려서 생깁니다.

### Supabase Auth: 로그인을 빌려 쓰기

로그인을 직접 만드는 것은 전문가에게도 어렵고 위험합니다. 비밀번호를 안전하게 저장하고, 비밀번호 찾기 메일을 보내고, 로그인 상태를 유지하는 일이 모두 까다롭습니다. 그래서 요즘은 **검증된 서비스의 로그인을 빌려 쓰는 것**이 상식입니다.

Supabase Auth가 해 주는 일:

- 이메일·비밀번호 회원가입, 로그인, 로그아웃
- 비밀번호는 원래 글자가 아니라 **되돌릴 수 없게 바꾼 값(해시)** 으로 저장
- 이메일 확인 메일, 비밀번호 재설정 메일
- 원하면 구글·카카오 같은 소셜 로그인도 연결 가능

<Analogy title="놀이공원 손목밴드">
  매표소(로그인)에서 신분을 확인하면 손목밴드(로그인 토큰)를 채워 줍니다. 그다음부터는 놀이기구마다 신분증을 다시 보여 줄 필요 없이 손목밴드만 보여 주면 됩니다. 밴드 색(권한)에 따라 탈 수 있는 기구가 다릅니다.
</Analogy>

## RLS: 줄마다 채우는 자물쇠

<Term id="rls">RLS</Term>(Row Level Security, 행 수준 보안)는 데이터베이스의 **한 줄 한 줄마다** "누가 읽고, 누가 만들고, 누가 고칠 수 있는지"를 정하는 규칙입니다.

7회의 엑셀 비유로 말하면, 모임 시트를 모두에게 공유하되 **각 줄에 "이 줄은 하늘 님만 고칠 수 있음"이라는 자물쇠**를 다는 것과 같습니다.

<Sim name="rls" />

### 우리 모임의 규칙

| 하고 싶은 일 | 누가 할 수 있나 | SQL에서는 |
| --- | --- | --- |
| 모임 목록 보기 | 누구나 (로그인 안 해도) | `select` 정책: `true` |
| 모임 만들기 | 로그인한 사람 | `insert` 정책: 로그인 확인 |
| 모임 고치기 | 그 모임을 만든 사람만 | `update` 정책: `auth.uid() = owner_id` |
| 모임 지우기 | 그 모임을 만든 사람만 | `delete` 정책: `auth.uid() = owner_id` |

`auth.uid()`는 "지금 요청한 사람의 회원 번호", `owner_id`는 "이 줄을 만든 사람의 회원 번호"입니다. 둘이 같을 때만 허락한다는 뜻입니다. 이 문장 하나만 읽을 수 있어도 오늘의 목표는 달성입니다.

<DeepDive title="RLS를 켜기만 하고 규칙을 안 만들면 어떻게 되나요">

RLS를 켜면 기본값은 **"아무도 안 됨"** 입니다. 그래서 규칙을 하나도 안 만들면 목록이 텅 비어 보입니다. 7회에 "목록이 비어 있어요"라는 문제를 겪었다면 바로 이 상태였습니다.

반대로 **RLS를 아예 끄면 "누구나 다 됨"** 입니다. 공개 키만 있으면 누구나 읽고, 고치고, 지울 수 있습니다. 가장 위험한 상태입니다.

| 상태 | 결과 | 위험 |
| --- | --- | --- |
| RLS 꺼짐 | 누구나 무엇이든 | 매우 위험 |
| RLS 켜짐, 규칙 없음 | 아무도 아무것도 못 함 | 안전하지만 안 쓰임 |
| RLS 켜짐, 규칙 있음 | 규칙대로 | 올바른 상태 |

</DeepDive>

## 열쇠는 금고에: 환경변수와 두 가지 키

### 환경변수

<Term id="env">환경변수</Term>는 비밀번호나 키처럼 **코드에 직접 적으면 안 되는 값**을 따로 보관하는 칸입니다.

- 내 컴퓨터: `.env.local` 파일 (`.gitignore` 덕분에 GitHub에 안 올라감)
- 배포 서버: Vercel의 **Settings → Environment Variables**

<Analogy title="현관 비밀번호를 쪽지에 써서 문에 붙이지 않는 것">
  코드는 GitHub에 올라가고, 공개 저장소라면 전 세계가 봅니다. 키를 코드에 적는 것은 현관 비밀번호를 쪽지에 써서 문에 붙여 두는 것과 같습니다.
</Analogy>

### 공개 키와 비밀 키

<Sim name="keys" />

| | <Term id="anon-key">공개 키</Term> (anon / publishable) | <Term id="service-key">비밀 키</Term> (service_role / secret) |
| --- | --- | --- |
| 비유 | 건물 출입 카드 | 건물 관리인의 만능 열쇠 |
| 할 수 있는 일 | RLS 규칙이 허락한 것만 | RLS를 무시하고 무엇이든 |
| 어디에 두나 | 브라우저 코드에 들어가도 됨 | 서버에만. 절대 화면 코드에 넣지 않음 |
| Next.js 이름 | `NEXT_PUBLIC_SUPABASE_…` | `NEXT_PUBLIC_`을 **붙이지 않음** |

<Callout type="warn" title="NEXT_PUBLIC_ 이라는 이름표의 뜻">
  Next.js에서 이름이 `NEXT_PUBLIC_`으로 시작하는 환경변수는 **브라우저로 내려가는 코드에 그대로 실립니다.** 누구나 볼 수 있다는 뜻입니다. 공개 키에는 붙여도 되지만, 비밀 키나 10회의 AI 키에는 절대 붙이면 안 됩니다.
</Callout>

### 키가 새어 나갔다면

실수로 키를 GitHub에 올렸거나 채팅창에 붙여 넣었다면, **파일을 지우는 것만으로는 부족합니다.** Git은 모든 기록을 남기기 때문에 예전 커밋에 키가 그대로 남아 있습니다.

1. 해당 서비스 대시보드에서 키를 **즉시 다시 발급(rotate)** 합니다. 예전 키는 쓸모없어집니다.
2. 새 키를 `.env.local`과 Vercel에 넣습니다.
3. 파일을 저장소에서 빼고 `.gitignore`에 추가합니다.

## 요즘 업계에서는

### 170개 앱의 문이 열려 있었다

2025년 봄, 한 보안 연구자가 AI 앱 빌더 Lovable로 만든 공개 앱 1,645개를 조사했더니 **170개(약 10%)** 에서 로그인하지 않은 누구나 개인정보를 읽을 수 있는 문제가 발견됐습니다. 원인은 오늘 배운 바로 그것, **Supabase 표에 RLS가 제대로 걸려 있지 않아** 공개 키만으로 데이터에 접근할 수 있었던 것입니다. 이 문제는 CVE-2025-48757이라는 번호로 등록됐습니다. ([위키백과 · Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding), [CVE-2025-48757](https://nvd.nist.gov/vuln/detail/CVE-2025-48757))

이 사건이 알려 주는 것:

- **AI가 만든 앱도 동작은 완벽해 보였습니다.** 화면에서는 아무 문제가 보이지 않습니다. 보안 구멍은 눈에 안 보입니다.
- 플랫폼 회사는 "앱 데이터를 지키는 책임은 앱을 만든 사람에게 있다"는 입장이었습니다. 즉, **만든 사람이 여러분이면 책임도 여러분에게** 있습니다.
- 해결책은 어렵지 않았습니다. 규칙 몇 줄과 **직접 막히는지 시험해 보는 습관**이면 충분했습니다.

### 개발자들도 AI를 다 믿지는 않는다

2025년 Stack Overflow 설문에서 개발자의 46%가 AI 도구의 정확성을 믿지 않는다고 답했습니다. 믿는다는 응답(33%)보다 많습니다. ([Stack Overflow 2025 설문 · AI](https://survey.stackoverflow.co/2025/ai)) 전문가들도 AI가 만든 결과를 **검증하는 것**을 당연한 일로 여긴다는 뜻입니다. 보안은 그중에서도 가장 먼저 검증할 부분입니다.

## 시연

강사가 다음을 보여 줍니다.

1. **RLS 없이** 공개 키만으로 데이터를 읽고 지우는 모습을 시험용 프로젝트에서 보여 줍니다. (실제 서비스에 해 보면 안 됩니다.)
2. Claude Code에게 RLS 규칙을 만들게 하고, 같은 시도가 막히는 것을 보여 줍니다.
3. 브라우저 두 개(일반 창과 시크릿 창)에 각각 다른 계정으로 로그인해, B 계정으로는 A의 모임에 수정 버튼이 안 보이고, 억지로 시도해도 거절되는 것을 확인합니다.
