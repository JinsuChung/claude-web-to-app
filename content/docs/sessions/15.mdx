## 오늘의 흐름

| 시간 | 내용 | 하는 일 |
| --- | --- | --- |
| 0–10분 | 지난 시간 돌아보기 | 설치 파일을 받은 사람들의 반응 나누기 |
| 10–40분 | 운영의 다섯 가지 | 피드백, 사용 통계, 에러 확인, 비용, 백업 |
| 40–55분 | 실습 1 | 의견 보내기 만들기, 운영 점검표 만들기 |
| 55–65분 | **쉬는 시간** | 발표 준비 |
| 65–100분 | 3분 데모 발표 | 한 사람씩 발표, 서로 한 줄 피드백 |
| 100–112분 | 15회 돌아보기와 요즘 흐름 | 배운 것 정리, 업계 흐름 속에서 우리의 위치 |
| 112–120분 | 다음 30일 계획 | 계속 배우는 길, 수료 |

마지막 시간입니다. 15회 동안 기획서와 목업에서 시작해 웹앱, 데이터베이스, 로그인, AI 기능, 그리고 휴대폰 앱까지 만들었습니다. 그런데 소프트웨어는 **출시하는 날이 끝이 아니라 시작**입니다. 오늘은 만든 것을 실제 사람들이 계속 쓰게 하는 법, 그리고 이 과정이 끝난 뒤 혼자 이어 가는 법을 배웁니다.

## 출시는 끝이 아니라 시작

<Analogy title="식당은 개업 날보다 그다음이 중요합니다">
  개업 날 음식이 아무리 맛있어도, 손님의 말을 듣지 않고, 어떤 메뉴가 팔리는지 모르고, 가스비가 얼마 나가는지 모르고, 장부를 잃어버린다면 오래가지 못합니다. 서비스도 같습니다. **듣고(피드백), 세고(통계), 살피고(에러), 아끼고(비용), 지키는(백업)** 일이 운영입니다.
</Analogy>

| --- | --- | --- |
| **피드백** | 쓰는 사람은 무엇이 불편한가? | 앱 안 "의견 보내기", 모임 때 직접 묻기 |
| **사용 통계** | 실제로 쓰이고 있나? | 이번 주 참석 신청 수, 새 회원 수 |

| **백업** | 데이터를 잃어버리면 어떻게 하나? | 한 달에 한 번 CSV로 내려받기 |

## 운영의 다섯 가지

### 1. 피드백: 쓰는 사람의 목소리

<Term id="feedback">피드백</Term>은 가장 값진 정보입니다. 내가 생각한 불편과 실제 사용자의 불편은 늘 다릅니다.

- **직접 묻기:** 모임이 끝날 때 "앱 쓰면서 불편했던 것 하나만 알려 주세요". 작은 서비스는 이것이 가장 좋습니다.
- **앱 안에서 받기:** 한 줄 의견과 별점만 받는 작은 칸을 만듭니다. 길게 쓰게 하면 아무도 쓰지 않습니다.
- **지켜보기:** 11–12회 과제처럼, 가족에게 휴대폰을 건네고 아무 설명 없이 써 보게 합니다. 어디서 멈칫하는지가 고칠 점입니다.

피드백을 모았으면 Claude에게 **"이 의견들을 비슷한 것끼리 묶고, 고치기 쉬운 순서와 효과가 큰 순서로 정리해줘"**라고 맡길 수 있습니다. 무엇을 먼저 고칠지는 사람이 정합니다.

### 2. 사용 통계: 질문부터 정하고 세기

### 3. 에러 확인: 고장은 조용히 납니다

회원이 쓰다가 에러를 만나도 대부분은 알려 주지 않고 그냥 떠납니다. 그래서 **운영자가 먼저 찾아봐야** 합니다.

| 어디서 | 무엇을 볼 수 있나 |
| --- | --- |
| Vercel 대시보드의 로그 | 웹앱 서버에서 난 에러, AI 기능 호출 실패 |
| Supabase 대시보드의 로그 | 데이터베이스 요청 실패, 보안 규칙에 막힌 요청 |
| Expo 대시보드 | 빌드와 업데이트 기록 |
| 에러 모니터링 도구 | 앱과 웹에서 난 에러를 모아 알림 (서비스가 커지면) |

일주일에 한 번, 10분만 이 화면들을 둘러보는 습관이면 충분합니다. 이상한 메시지가 보이면 복사해서 Claude Code에 붙여 넣으세요. 이 과정 내내 해 온 그대로입니다.

### 5. 백업: 잃어버리기 전에

2025년 7월, AI 코딩 도구(Replit)의 에이전트가 "아무것도 바꾸지 말라"는 지시에도 실제 서비스의 데이터베이스를 지워 버린 사례가 알려져 화제가 됐습니다 ([위키백과: Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding)). 7회에도 이야기했지만, 운영 단계에서는 더 중요합니다.

- **코드**는 Git과 GitHub가 지켜 줍니다(5회). 실수하면 되돌리면 됩니다.
- **데이터**는 Git에 들어 있지 않습니다. 따로 내려받아 두어야 합니다.
- 실제 회원 데이터가 들어간 프로젝트에서 Claude Code가 데이터를 지우거나 바꾸는 명령을 실행하려 하면, **승인하기 전에 무엇을 하는지 꼭 읽어 보세요.**

<PromptCard id="backup-export" />

<DeepDive title="운영자를 위한 작은 습관 다섯 가지">

1. **주 1회 10분 점검:** 로그 둘러보기, 의견 읽기, 숫자 하나 확인.
2. **고치기 전에 커밋:** 실제 회원이 쓰는 서비스는 고치기 전에 지금 상태를 저장해 둡니다.
3. **큰 변경은 따로 시험:** 새 기능은 가상 데이터로 먼저 시험하고 내놓습니다.
4. **공지하고 바꾸기:** 화면이 크게 바뀌면 회원들에게 미리 알립니다.
5. **그만둘 때도 깔끔하게:** 서비스를 닫을 때는 회원에게 알리고, 데이터를 지우고, 키를 폐기합니다. 1회에 배운 "일회용 소프트웨어"도 끝맺음은 책임 있게 합니다.

</DeepDive>

## 15회 돌아보기

### 우리가 지나온 길

| 단계 | 회차 | 만든 것 | 익힌 힘 |
| --- | --- | --- | --- |
| 시작하기 | 1–3회 | 기획서, 목업, 첫 웹페이지 | 무엇을 만들지 **말로 정하는 힘** |
| 웹앱 만들기 | 4–6회 | 내 PC의 웹앱 → GitHub → 인터넷 공개 | 저장하고, 되돌리고, **공개하는 힘** |
| 데이터와 로그인 | 7–9회 | 데이터베이스, 로그인, 보안 규칙, 기능 | **지키는 힘** (RLS, 키 관리) |
| AI 기능 | 10회 | 서비스 안에서 일하는 Claude | AI를 **부품으로 쓰는 힘** |
| 앱으로 | 11–14회 | PWA, Expo 앱, 데이터 연결, 출시 준비 | 웹에서 **앱으로 넓히는 힘** |
| 마무리 | 15회 | 운영 점검표, 데모 | **키우는 힘** |

그리고 모든 회차에 공통으로 있었던 것이 있습니다. **계획 먼저 보기, 결과 직접 확인하기, 에러는 그대로 붙여 넣기, 비밀 키는 지키기.** 이것이 이 과정에서 가장 오래 남을 습관입니다.

## 요즘 업계에서는

### 바닥은 올라갔고, 천장은 우리가 올립니다

1회에 2025년 2월 안드레이 카파시가 "바이브 코딩"이라는 말을 처음 썼고, 이 말이 그해 콜린스 사전 올해의 단어로 뽑혔다는 이야기로 시작했습니다 ([위키백과: Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding)). 그리고 2026년에는 "에이전틱 엔지니어링"이라는 말이 널리 쓰이기 시작했습니다. AI 에이전트가 만들고, 사람은 요구사항을 정하고 계획을 검토하고 결과를 검증하는 방식입니다.

흔히 이렇게 정리됩니다. **바이브 코딩은 누구나 만들 수 있게 "바닥"을 올렸고, 에이전틱 엔지니어링은 잘 만드는 사람의 "천장"을 올린다.** 여러분은 15회 동안 두 가지를 다 경험했습니다. 말로 만들어 보는 즐거움(바닥), 그리고 계획을 검토하고 보안 규칙을 확인하고 테스트 체크리스트로 검증하는 습관(천장).

### "확인하는 힘"이 실력입니다

AI의 코딩 실력은 계속 올라가고 있습니다. 실제 소프트웨어 문제를 고치게 하는 평가(SWE-bench Verified)에서 2026년 9월 기준 Claude Opus 5가 97.0%를 기록했습니다 ([Vals.ai SWE-bench](https://www.vals.ai/benchmarks/swebench)). 그런데도 현장의 개발자들은 여전히 확인합니다. 2025년 Stack Overflow 설문에서 개발자의 84%가 AI 도구를 쓰거나 쓸 계획이라고 답했지만, 46%는 AI 결과의 정확성을 믿지 않는다고 했고, 66%는 "거의 맞지만 조금 틀린 결과"를 가장 큰 불만으로 꼽았습니다 ([Stack Overflow 2025 Developer Survey](https://survey.stackoverflow.co/2025/)).

**AI가 만드는 시대에 사람의 실력은 "무엇을 만들지 정하고, 맞게 됐는지 확인하는 힘"**입니다. 이것은 코딩 경험보다 살면서 쌓은 경험, 즉 무엇이 불편한지 아는 눈과 꼼꼼함에서 나옵니다.

### 작은 소프트웨어의 시대

a16z의 [「일회용 소프트웨어(Disposable Software)」](https://a16z.com/disposable-software/)는 아이를 위한 수학 게임, 친구 몇 명을 위한 사진 공유 앱처럼 **크게 키우거나 돈을 벌려는 것이 아닌 작고 개인적인 앱**을 사람들이 직접 만들어 쓰는 흐름을 소개합니다. 우리 모임 서비스도 그런 소프트웨어입니다. 수백만 명이 아니라 우리 동네 열두 명을 위한 앱. 그런 앱을 만들 수 있다는 것이 지금 시대가 준 선물입니다.
