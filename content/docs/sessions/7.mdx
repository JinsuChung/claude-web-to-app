## 지금 웹앱의 한계

6회까지 만든 웹앱에는 모임 일정이 **코드 안에** 적혀 있습니다. 그래서

- 새 모임을 추가하려면 Claude Code에게 코드를 고치게 하고, 커밋·푸시하고, 배포를 기다려야 합니다.
- 회원이 화면에서 무언가를 입력해도 **어디에도 저장되지 않습니다**. 새로 고치면 사라집니다.
- 내 휴대폰에서 입력한 것을 다른 사람이 볼 수 없습니다.

<Analogy title="인쇄한 안내문 vs 함께 쓰는 공책">
  지금 웹앱은 인쇄해서 나눠 준 안내문과 같습니다. 내용을 바꾸려면 다시 인쇄해야 하지요. 오늘은 이것을 **모두가 같이 펼쳐 보고 적을 수 있는 공책**으로 바꿉니다. 그 공책이 데이터베이스입니다.
</Analogy>

## 데이터베이스는 똑똑한 엑셀

<Term id="database">데이터베이스</Term>는 데이터를 정리해 저장해 두는 곳입니다. 처음에는 **여러 사람이 동시에 쓰는 엑셀 파일**이라고 생각하면 충분합니다.

| 엑셀 | 데이터베이스 | 예시 |
| --- | --- | --- |
| 파일 | 데이터베이스 | 우리 모임 데이터 전체 |
| 시트 | <Term id="table">테이블</Term> | 모임 일정 시트, 회원 시트 |
| 맨 윗줄 제목 | <Term id="column">열(컬럼)</Term> | 제목, 날짜, 장소, 정원 |
| 한 줄 | <Term id="row">행(로우)</Term> | "10월 정기 모임, 10/18, 북카페 한모금, 12명" |

### 엑셀과 무엇이 다른가

엑셀로도 모임 일정을 관리할 수 있는데, 왜 데이터베이스를 쓸까요?

| | 엑셀 | 데이터베이스 |
| --- | --- | --- |
| 동시에 쓰기 | 두 사람이 같이 고치면 꼬이기 쉬움 | 수천 명이 동시에 써도 안전 |
| 규칙 | 날짜 칸에 아무 글이나 들어감 | "날짜 칸에는 날짜만" 같은 규칙을 강제 |
| 크기 | 수십만 줄이면 느려짐 | 수백만 줄도 빠르게 찾음 |
| 웹앱과 연결 | 어려움 | 웹앱·휴대폰 앱이 바로 읽고 씀 |
| 누가 무엇을 볼지 | 파일을 공유하면 다 보임 | 줄마다 볼 수 있는 사람을 정할 수 있음 (8회) |

### 칸마다 "종류"가 정해져 있다

데이터베이스는 칸마다 어떤 종류의 값이 들어갈지 미리 정합니다. 덕분에 "정원" 칸에 "열두 명"이라고 쓰는 실수를 막아 줍니다.

| 칸 이름 | 종류 | 뜻 |
| --- | --- | --- |
| `id` | 자동 번호 | 줄마다 붙는 고유 번호. 주민번호처럼 겹치지 않음 |
| `title` | 글자(text) | 모임 제목 |
| `starts_at` | 날짜와 시간 | 모임 시작 시각 |
| `place` | 글자 | 장소 |
| `capacity` | 숫자(integer) | 정원 |
| `created_at` | 날짜와 시간 | 줄이 만들어진 시각 (자동) |

<Callout title="칸 이름이 영어인 이유">
  화면에는 한글로 보여 주지만, 칸 이름은 보통 영어 소문자와 밑줄(`starts_at`)로 씁니다. 프로그램끼리 주고받을 때 탈이 적기 때문입니다. 이름을 정하는 것은 Claude가 알아서 해 줍니다.
</Callout>

## SQL, 읽을 줄만 알면 됩니다

<Term id="sql">SQL</Term>은 데이터베이스에 일을 시키는 말입니다. 직접 쓸 필요는 없지만, **Claude가 만든 SQL을 실행하기 전에 무엇을 하는지 읽을 수 있으면** 큰 사고를 막을 수 있습니다. 다행히 SQL은 영어 문장과 비슷합니다.

| SQL | 엑셀로 치면 | 위험도 |
| --- | --- | --- |
| `select * from meetups` | 모임 시트 전체 보기 | 안전 |
| `select title from meetups where capacity > 10` | 정원이 10명보다 많은 모임의 제목만 필터 | 안전 |
| `insert into meetups (title) values ('11월 모임')` | 새 줄 추가 | 보통 |
| `update meetups set place = '구민회관' where id = 3` | 3번 줄의 장소 고치기 | 주의 |
| `delete from meetups where id = 3` | 3번 줄 지우기 | 위험 |
| `drop table meetups` | 시트 통째로 삭제 | 매우 위험 |

<Callout type="warn" title="이 단어가 보이면 멈추고 물어보세요">
  `delete`, `drop`, `truncate`, 그리고 `where` 없는 `update`. 실행하기 전에 "이 SQL이 무엇을 지우거나 바꾸는지 설명해줘"라고 꼭 물어보세요.
</Callout>

## Supabase는 무엇인가

<Term id="supabase">Supabase</Term>는 데이터베이스를 인터넷에서 빌려 쓰게 해 주는 서비스입니다. 6회의 Vercel이 웹앱을 올리는 곳이라면, Supabase는 **데이터를 올리는 곳**입니다.

- 데이터베이스(PostgreSQL이라는 오래되고 믿을 만한 종류)
- 회원가입·로그인 (8회)
- 사진 같은 파일 저장 (9회)
- 웹에서 엑셀처럼 표를 보고 고칠 수 있는 화면(Table Editor)

무료 요금제는 <Fact k="supabase.free" />. 실습에는 충분하지만, **1주일 동안 쓰지 않으면 프로젝트가 잠시 멈춥니다.** 대시보드에서 다시 켜면 되니 놀라지 마세요.

<Analogy title="Vercel은 식당 홀, Supabase는 창고와 장부">
  손님이 보는 화면은 Vercel에서, 손님이 주문한 기록과 재고는 Supabase에서. 웹앱은 둘을 이어 주는 직원입니다.
</Analogy>

### 웹앱과 데이터베이스는 어떻게 대화할까

```
[휴대폰 브라우저] ──"모임 목록 줘"──▶ [웹앱 (Vercel)] ──"select …"──▶ [데이터베이스 (Supabase)]
                  ◀──── 화면 ─────                  ◀──── 표 ────────
```

웹앱이 데이터베이스에 접속하려면 **주소**와 **열쇠(키)** 가 필요합니다. 이 두 가지는 코드에 직접 적지 않고 <Term id="env">환경변수</Term> 파일(`.env.local`)에 따로 둡니다. 5회에 배운 `.gitignore` 덕분에 이 파일은 GitHub에 올라가지 않습니다.

<DeepDive title="공개 키(anon key)는 정말 공개해도 되나요">

Supabase가 주는 키에는 두 종류가 있습니다.

- **공개 키(anon / publishable)**: 웹앱 화면에 실려 누구나 볼 수 있다는 전제로 만든 키입니다. 대신 이 키로 할 수 있는 일은 **보안 규칙(RLS)** 이 정한 범위까지입니다.
- **비밀 키(service_role / secret)**: 모든 규칙을 무시하고 무엇이든 할 수 있는 만능 열쇠입니다. 절대 화면 코드에 넣으면 안 됩니다.

오늘은 공개 키만 씁니다. 그런데 공개 키는 누구나 볼 수 있으니, 보안 규칙이 없으면 **누구나 우리 데이터를 읽고 지울 수 있습니다.** 그래서 8회에 보안 규칙을 반드시 다룹니다. 오늘은 가상 데이터만 넣으니 괜찮습니다.

</DeepDive>

## 요즘 업계에서는

### AI 앱 빌더의 단골 짝꿍, Supabase

요즘 말로 앱을 만들어 주는 서비스들은 데이터 저장소로 Supabase를 많이 씁니다. 예를 들어 Lovable은 내 Supabase 프로젝트를 연결해 데이터베이스, 로그인, 파일 저장을 맡기는 기능을 공식으로 제공합니다. ([Lovable 문서 · Supabase 연동](https://docs.lovable.dev/integrations/supabase))

이유는 간단합니다. 표를 엑셀처럼 볼 수 있고, 로그인과 파일 저장이 한곳에 있고, 무료로 시작할 수 있기 때문입니다. 이 과정에서 Supabase를 고른 이유도 같습니다. 12–13회에 만드는 휴대폰 앱도 **같은 Supabase**를 씁니다.

### "AI가 데이터베이스를 지웠다"

2025년 7월, 한 스타트업 창업자가 AI 코딩 도구(Replit)의 에이전트가 "아무것도 바꾸지 말라"는 지시에도 불구하고 데이터베이스를 지워 버렸다고 공개해 화제가 됐습니다. ([위키백과 · Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding))

이 사건이 주는 교훈은 세 가지입니다.

1. **지우는 SQL은 사람이 읽고 승인한다.** Claude Code가 명령을 실행하기 전에 묻는 것은 귀찮은 절차가 아니라 안전장치입니다.
2. **연습용과 진짜를 분리한다.** 실제 회원 데이터가 생기면 연습용 프로젝트를 따로 둡니다.
3. **백업을 확인한다.** 유료 요금제에는 자동 백업이 있고, 무료에서는 중요한 표를 가끔 내려받아 둡니다(Table Editor → Export).

## 시연

강사가 다음을 보여 줍니다.

1. 엑셀 파일로 정리한 가상 모임 일정 표를 보여 주고, 같은 내용을 Supabase Table Editor에 만듭니다. "시트가 테이블이 됐다"는 것을 눈으로 확인합니다.
2. Claude Code에게 기획서를 보여 주고 테이블 설계를 받습니다. 설계 표를 함께 읽으며 "정원 칸은 왜 숫자인가요?" 같은 질문을 던져 봅니다.
3. 웹앱을 연결한 뒤 화면에서 모임을 추가하면, Supabase 표에 **실시간으로 줄이 생기는 것**을 나란히 띄워 보여 줍니다.
