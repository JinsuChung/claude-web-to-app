## 오늘의 흐름

| 시간 | 내용 | 하는 일 |
| --- | --- | --- |
| 0–10분 | 지난 시간 돌아보기 | 휴대폰에서 앱 열어 보기, 과제에서 나온 불편한 점 |
| 10–40분 | 앱과 데이터베이스 | 데이터베이스 하나·화면 둘, 공개 키와 보안 규칙, 로그인 유지 |
| 40–50분 | 요즘 업계에서는 | 백엔드 서비스(BaaS), Expo 공식 Supabase 안내, 앱 보안 사고 |
| 50–60분 | 시연 | 웹에서 모임을 만들면 앱에 바로 뜨는 장면 |
| 60–70분 | **쉬는 시간** | |
| 70–110분 | 실습 | 앱에 Supabase 연결 → 로그인 → 같은 데이터 확인 → 상태 화면 |
| 110–120분 | 정리와 퀴즈 | 보안 점검, 다음 시간(빌드와 출시) 안내 |

지난 시간 앱은 겉모습은 그럴듯했지만 **가짜 데이터**였습니다. 오늘은 7–9회에 만든 Supabase 데이터베이스를 앱에도 연결합니다. 그러면 웹에서 만든 모임이 앱에 뜨고, 앱에서 참석 신청한 것이 웹에도 보입니다.

## 데이터베이스 하나, 화면 둘

<Analogy title="은행 계좌와 통장, 앱">
  내 돈은 은행(데이터베이스)에 있습니다. 같은 계좌를 은행 창구(웹앱)에서 봐도, 휴대폰 은행 앱(네이티브 앱)에서 봐도 잔액은 같습니다. 창구가 둘이라고 돈이 두 군데 있는 것이 아닙니다. 우리 모임도 마찬가지입니다. 모임과 참석 기록은 **Supabase 한 곳**에 있고, 웹앱과 앱은 그것을 보여 주는 **두 개의 창구**입니다.
</Analogy>

```text
            ┌──────────────┐
웹앱 ──────▶│              │
(Vercel)    │   Supabase   │  모임, 참석 신청, 회원, 사진
            │ (데이터베이스) │
앱 ────────▶│              │
(Expo)      └──────────────┘
```

이 구조의 장점은 분명합니다.

- **데이터를 두 번 관리하지 않습니다.** 모임을 한 번 만들면 어디서나 보입니다.
- **보안 규칙도 한 곳에서** 지킵니다. 8회에 만든 <Term id="rls">RLS</Term>(행 수준 보안)가 웹과 앱 모두에 똑같이 적용됩니다.
- **회원 계정도 하나입니다.** 웹에서 가입한 이메일로 앱에서도 로그인합니다.

## 앱에 넣어도 되는 키, 절대 넣으면 안 되는 키

8회에 배운 두 가지 키를 다시 떠올려 봅시다.

| 키 | 비유 | 웹앱에서 | 앱에서 |
| --- | --- | --- | --- |
| Supabase 주소 + <Term id="anon-key">공개 키</Term> | 건물 주소와 출입증 | 화면 코드에 들어가도 됨 | **앱에 들어가도 됨** |
| Supabase <Term id="service-key">비밀 키</Term> | 건물 마스터키 | 서버(환경변수)에만 | **절대 넣지 않음** |
| 데이터베이스 비밀번호 | 금고 비밀번호 | 넣지 않음 | **절대 넣지 않음** |
| Claude <Term id="api-key">API 키</Term> | 내 신용카드 | 서버(환경변수)에만 | **절대 넣지 않음** |

<Sim name="keys" />

왜 앱은 더 조심해야 할까요? 웹앱의 서버 코드는 Vercel 안에 숨어 있지만, **앱 설치 파일은 누구나 내려받아 열어 볼 수 있기 때문**입니다. 앱 안에 넣은 값은 모두 공개된 것으로 생각해야 합니다.

Expo의 공식 Supabase 안내도 같은 이야기를 합니다. Supabase 주소와 공개 키는 원래 공개되는 값이라 **보안은 RLS에 달려 있으니 앱이 쓰는 모든 테이블에 RLS를 켜고 규칙을 만들라**고, 그리고 **비밀 키는 RLS를 건너뛰어 모든 데이터에 접근하므로 앱에 절대 넣지 말라**고 강조합니다 ([Expo: Using Supabase](https://docs.expo.dev/guides/using-supabase/)).

<Callout title="AI 기능은 앱에서 어떻게?">
  10회에 만든 AI 요약 기능은 Claude API 키가 필요합니다. 이 키는 앱에 넣을 수 없으니, **앱은 웹앱의 서버(Vercel)에 "요약해 줘"라고 부탁하고, 서버가 키를 써서 Claude를 부르는** 구조로 만듭니다. 오늘은 데이터 연결에 집중하고, AI 기능은 선택 과제로 남겨 둡니다.
</Callout>

## 로그인이 유지되는 앱

휴대폰 앱은 껐다 켤 때마다 다시 로그인하라고 하면 아무도 쓰지 않습니다. 그래서 로그인 정보(세션)를 **휴대폰 안에 안전하게 저장**해 두었다가 다시 켰을 때 꺼내 씁니다.

<Analogy title="놀이공원 손목 밴드">
  입구에서 표를 확인받으면(로그인) 손목 밴드(세션)를 채워 줍니다. 밴드가 있으면 놀이기구마다 표를 다시 보여 줄 필요가 없습니다. 밴드는 시간이 지나면 새것으로 바꿔 줍니다(자동 갱신). 앱도 휴대폰 안에 이 밴드를 보관해 두는 것입니다.
</Analogy>

Expo 공식 안내는 Supabase 로그인 정보를 휴대폰 안의 저장소(expo-sqlite)에 보관하고, 앱이 화면에 나와 있을 때만 로그인 정보를 자동으로 새로 고치도록 설정하는 방법을 보여 줍니다. 이런 세부 설정은 Claude Code가 공식 안내대로 해 줍니다. 우리는 **"앱을 껐다 켜도 로그인이 유지되는지"**를 확인하면 됩니다.

## 데이터를 가져오는 앱의 네 가지 상태

데이터베이스에서 모임을 가져오는 화면은 늘 네 가지 상태 중 하나입니다. 가짜 데이터일 때는 신경 쓸 일이 없었지만, 이제는 모두 챙겨야 합니다.

| 상태 | 언제 | 화면에 보여 줄 것 |
| --- | --- | --- |
| **불러오는 중** | 데이터가 오는 중 | 빙글빙글 표시나 회색 빈 카드 |
| **비어 있음** | 모임이 하나도 없을 때 | "아직 모임이 없어요" + 만들기 안내 |
| **에러** | 서버 문제, 권한 문제 | "불러오지 못했어요" + 다시 시도 버튼 |
| **인터넷 끊김** | 지하철, 엘리베이터 | "인터넷 연결을 확인해 주세요" |

<Analogy title="식당 주문">
  주문하자마자 음식이 나오지는 않습니다. 좋은 식당은 "조리 중입니다"(로딩), "오늘은 그 메뉴가 다 떨어졌어요"(비어 있음), "주방에 문제가 생겨 다시 주문해 주세요"(에러)를 손님에게 알려 줍니다. 아무 말 없이 빈 접시만 내오는 식당에는 다시 가지 않습니다.
</Analogy>

<DeepDive title="새로 고침과 실시간 반영">

웹에서 모임을 만들었을 때 앱에 바로 나타나게 하는 방법은 두 가지입니다.

- **당겨서 새로 고침:** 목록을 아래로 끌어당기면 다시 불러옵니다. 휴대폰 앱에서 가장 익숙한 방식이고 만들기도 쉽습니다.
- **실시간 반영:** Supabase의 실시간(Realtime) 기능을 쓰면 데이터가 바뀌는 순간 화면이 저절로 바뀝니다. 채팅처럼 즉시성이 중요할 때 씁니다.

우리 모임처럼 일정이 하루에 몇 번 바뀌는 서비스는 **당겨서 새로 고침**으로 충분합니다. 기능은 필요할 때 더하는 것이 좋습니다.

</DeepDive>

## 요즘 업계에서는

### 서버를 직접 만들지 않는 시대: BaaS

예전에는 앱을 만들려면 데이터를 저장하고 로그인을 처리하는 **서버를 직접 만들어야** 했습니다. 요즘은 Supabase 같은 서비스가 데이터베이스, 로그인, 파일 저장, 보안 규칙을 한꺼번에 제공합니다. 이런 서비스를 BaaS(Backend as a Service, 서비스로 받는 백엔드)라고 부릅니다. 작은 팀이나 혼자 만드는 사람도 웹과 앱을 함께 운영할 수 있게 된 큰 이유입니다.

Expo는 공식 문서에 Supabase 연결 안내를 따로 두고 있고, `eas integrations:supabase:connect`라는 명령 한 줄로 필요한 부품 설치와 주소·공개 키 설정을 해 주는 방법도 소개합니다 ([Expo: Using Supabase](https://docs.expo.dev/guides/using-supabase/)). 그만큼 **Expo + Supabase**가 흔한 조합이 됐다는 뜻입니다.

### 빠르게 만들수록 보안 점검은 더 중요해졌습니다

AI로 빠르게 만든 앱에서 보안 문제가 드러난 사례가 실제로 보고됐습니다. AI 앱 빌더 Lovable로 만든 공개 앱 1,645개를 조사했더니 170개에서 누구나 개인 데이터에 접근할 수 있는 취약점이 발견됐다는 조사가 있었습니다 ([위키백과: Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding)). 대부분 **보안 규칙(RLS)이 없거나 허술한 경우**였습니다.

교훈은 단순합니다. **AI에게 만들게 했으면, 점검도 AI에게 시키고, 확인은 사람이 직접** 합니다. 오늘 실습 마지막에 보안 점검을 꼭 하는 이유입니다.

## 시연

강사가 Expo 앱에 Supabase를 연결합니다. 웹앱과 **같은 Supabase 프로젝트**의 주소와 공개 키만 앱에 넣는 장면을 보여 줍니다. 노트북 브라우저의 웹앱에서 "11월 모임 · 『작은 것들의 신』"을 새로 만들고, 휴대폰 앱에서 목록을 당겨 새로 고침해 바로 나타나는 것을 확인합니다. 반대로 앱에서 참석 신청을 하면 웹앱의 남은 자리가 줄어드는 것도 보여 줍니다. 마지막으로 비행기 모드를 켜서 인터넷 끊김 화면을 확인합니다.
