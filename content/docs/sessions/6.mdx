## 지금 내 웹앱은 어디에 있나요

지난 4–5회에 만든 웹앱은 지금 두 군데에 있습니다.

1. **내 컴퓨터**: `http://localhost:3000`으로 열립니다. 하지만 이 주소는 **내 컴퓨터 안에서만** 통합니다. 옆 사람이 같은 주소를 입력해도 열리지 않습니다.
2. **GitHub**: 코드가 보관돼 있습니다. 하지만 GitHub는 **코드를 보관하는 창고**이지, 웹앱을 실행해 보여 주는 곳이 아닙니다.

<Analogy title="요리 레시피와 식당">
  지금 상황은 맛있는 요리 레시피(코드)를 만들어 집 부엌(내 컴퓨터)에서 요리해 본 것, 그리고 레시피를 금고(GitHub)에 넣어 둔 것과 같습니다. 손님이 그 요리를 먹으려면 **식당**이 필요합니다. 식당을 열어 주는 곳이 오늘 배우는 Vercel입니다.
</Analogy>

## 웹은 어디에 사는가

### 서버: 24시간 켜져 있는 컴퓨터

<Term id="server">서버</Term>는 특별한 기계가 아니라 **하루 종일 꺼지지 않고 인터넷에 연결된 컴퓨터**입니다. 누군가 주소를 입력하면 서버가 웹페이지를 보내 줍니다.

- 내 노트북도 웹페이지를 보여 줄 수는 있지만, 덮개를 닫거나 와이파이가 끊기면 끝입니다.
- 그래서 웹 서비스는 데이터센터에 있는 서버 위에서 돌아갑니다.

### 호스팅: 서버를 빌려 쓰기

예전에는 서버를 직접 사서 관리해야 했습니다. 지금은 서버 공간을 **빌려 쓰는** <Term id="hosting">호스팅</Term> 서비스가 일반적입니다. 집을 짓는 대신 원룸을 빌리는 것과 같습니다.

| 예전 방식 | 요즘 방식 |
| --- | --- |
| 서버 컴퓨터 구입, 전기·냉방·보안 관리 | 서비스에 가입하고 연결만 하면 끝 |
| 운영체제 설치, 프로그램 설정 | 대부분 자동 |
| 사람이 몰리면 서버를 더 사야 함 | 사람이 몰리면 자동으로 늘어남 |
| 전문 인력 필요 | 혼자서도 가능 |

### 배포: 식당 문을 여는 일

<Term id="deploy">배포</Term>는 내 코드를 서버에 올려 **누구나 쓸 수 있게 공개하는 일**입니다. 배포할 때는 보통 두 가지가 일어납니다.

1. **빌드(<Term id="build">build</Term>)**: 개발용 코드를 손님에게 내놓을 수 있는 완성품으로 만듭니다. 재료를 손질하고 요리를 완성해 접시에 담는 과정입니다.
2. **올리기**: 완성품을 서버에 올리고 주소를 붙입니다.

빌드 중에 문제가 있으면 배포가 실패합니다. 요리 중에 재료가 하나 빠진 것을 발견한 것과 같습니다. 실패해도 **이전에 배포된 버전은 그대로 열립니다**. 손님은 어제 메뉴를 그대로 먹을 수 있으니 안심하세요.

### 도메인: 가게 간판

<Term id="domain">도메인</Term>은 `our-moim.vercel.app`처럼 사람이 기억하기 쉬운 주소입니다. 실제로 컴퓨터끼리는 숫자 주소로 찾아가지만, 사람은 이름이 편하니까 간판을 붙이는 셈입니다.

- Vercel은 `프로젝트이름.vercel.app` 주소를 **무료로** 줍니다.
- `ourmoim.kr` 같은 나만의 주소가 필요하면 도메인을 따로 사서(1년에 1–3만 원대가 흔합니다) 연결합니다. 오늘은 무료 주소로 충분합니다.

<DeepDive title="주소를 입력하면 무슨 일이 일어날까요">

1. 휴대폰 브라우저에 `our-moim.vercel.app`을 입력합니다.
2. 인터넷의 "전화번호부"(DNS)가 이 이름에 해당하는 서버의 숫자 주소를 알려 줍니다.
3. 브라우저가 그 서버에 "첫 화면 주세요"라고 요청합니다.
4. 서버가 HTML, CSS, JavaScript를 보내 주고, 브라우저가 그것을 화면으로 그립니다.

이 모든 일이 1초도 안 되는 사이에 일어납니다. Vercel은 전 세계 여러 곳에 복사본을 두기 때문에 한국에서 열어도 빠릅니다.

</DeepDive>

## Vercel은 무엇이 편한가

<Term id="vercel">Vercel</Term>은 4회에 쓴 <Term id="nextjs">Next.js</Term>를 만든 회사의 호스팅 서비스입니다. 그래서 Next.js 웹앱과 궁합이 가장 좋습니다.

가장 큰 장점은 **GitHub와 연결해 두면 푸시할 때마다 자동으로 다시 배포**한다는 점입니다.

<Sim name="deploy-pipeline" />

| 단계 | 하는 사람 | 걸리는 시간 |
| --- | --- | --- |
| 코드 고치기 | Claude Code (내가 말로 지시) | 몇 초–몇 분 |
| 커밋·푸시 | Claude Code | 몇 초 |
| 빌드·배포 | Vercel (자동) | 1–2분 |
| 확인 | 나 | 몇 초 |

5회에 배운 커밋·푸시가 이제 **업데이트 버튼**이 됩니다. 한 번 연결해 두면 다시 Vercel 화면에 들어갈 일이 거의 없습니다.

<Analogy title="자동으로 인쇄되는 신문">
  GitHub에 원고를 넣으면(푸시) 인쇄소(Vercel)가 알아서 인쇄해 배달까지 해 주는 신문사와 같습니다. 원고를 고쳐 다시 넣으면 다음 판이 자동으로 나옵니다.
</Analogy>

### 미리보기 배포

Vercel은 기본 줄기(main)가 아닌 다른 가지(branch)에 올리면 **미리보기 주소**를 따로 만들어 줍니다. 진짜 주소는 그대로 두고, 바뀐 버전을 먼저 확인해 볼 수 있습니다. 처음에는 몰라도 되지만, 나중에 "고친 걸 회원들에게 공개하기 전에 먼저 보고 싶다"는 생각이 들면 기억해 두세요.

## 무료 요금제와 공개 주소, 꼭 알아야 할 것

### Vercel 무료(Hobby) 요금제

- 무료 요금제: <Fact k="vercel.hobby" />
- 이 과정의 실습, 개인 프로젝트, 동네 모임 서비스에는 충분합니다.
- 단, **비상업·개인 용도**입니다. 가게 홍보나 유료 서비스처럼 돈을 버는 목적이라면 Pro 요금제(<Fact k="vercel.pro" />)를 검토해야 합니다.

### 배포 주소는 누구나 열 수 있습니다

배포하는 순간 주소를 아는 **누구나** 들어올 수 있습니다. 검색엔진에 잡힐 수도 있습니다.

<Callout type="warn" title="올리기 전에 꼭 확인">
  - 실제 회원 이름, 전화번호, 주소가 코드나 화면에 들어 있지 않은지
  - 비밀번호나 키가 코드에 적혀 있지 않은지 (8회에서 자세히 다룹니다)
  - 지금은 가상 데이터만 쓰고 있는지
</Callout>

| 괜찮은 것 | 올리면 안 되는 것 |
| --- | --- |
| 모임 소개, 가상 일정 | 실제 회원 연락처 목록 |
| 지어낸 장소 이름 | 집 주소, 주민번호 |
| 화면 디자인 | API 키, 비밀번호 |

## 요즘 업계에서는

### 배포가 "전문가의 일"에서 "버튼 하나"로

10년 전만 해도 웹 서비스를 공개하려면 서버를 빌리고, 프로그램을 설치하고, 보안 설정을 하는 데 며칠이 걸렸습니다. 지금은 Vercel, Netlify, Cloudflare 같은 서비스가 이 과정을 자동으로 처리합니다. 덕분에 "만들기"와 "공개하기" 사이의 거리가 몇 분으로 줄었습니다.

- 요즘 나오는 AI 앱 빌더(Lovable, Replit, v0 등)는 아예 **만들자마자 공개 주소**를 줍니다.
- 이 과정은 그 편리함을 그대로 누리되, 코드를 GitHub에 직접 두고 Vercel에 연결하는 방식을 씁니다. 도구를 바꾸고 싶을 때 코드를 들고 나갈 수 있고, 무슨 일이 일어나는지 이해할 수 있기 때문입니다.

### "거의 맞는데 조금 틀린" 결과

배포가 쉬워진 만큼, **확인 없이 공개하는 실수**도 쉬워졌습니다. 2025년 Stack Overflow 개발자 설문에서 가장 많이 꼽힌 불만(66%)이 "AI가 만든 결과가 거의 맞지만 조금 틀리다"였고, 45%는 "AI가 만든 코드를 고치는 데 시간이 더 든다"고 답했습니다. ([Stack Overflow 2025 설문 · AI](https://survey.stackoverflow.co/2025/ai))

전문 개발자도 이렇게 느낀다는 것은, 배포 전에 **직접 눌러 보는 확인**이 여전히 사람의 몫이라는 뜻입니다. 오늘 실습에 "배포 후 점검"을 넣은 이유입니다.

<Analogy title="인쇄 전 교정쇄">
  출판사는 책을 대량으로 찍기 전에 꼭 교정쇄를 뽑아 읽어 봅니다. 배포가 빨라진 지금은 "찍고 나서 고치기"도 쉽지만, 사람들이 처음 받아 보는 화면이 엉망이면 신뢰를 잃습니다.
</Analogy>

## 시연

강사가 다음을 차례로 보여 줍니다.

1. Vercel에서 GitHub 저장소를 연결하고 **Deploy**를 누릅니다. 빌드 로그가 올라가는 모습을 함께 봅니다.
2. 1–2분 뒤 나온 주소를 QR 코드로 띄우고, 수강생들이 휴대폰으로 엽니다.
3. Claude Code에게 "제목을 바꾸고 커밋·푸시해줘"라고 말합니다. 1분 뒤 모두의 휴대폰을 새로 고치면 제목이 바뀌어 있습니다.
4. 일부러 오타를 넣어 빌드를 실패시킨 뒤, 빨간 에러 로그를 복사해 Claude Code에 붙여 넣고 고치는 장면을 보여 줍니다. 그동안 기존 주소는 멀쩡히 열리는 것도 확인합니다.
