## 이 과정에서 만드는 것

15번의 수업이 끝나면 여러분 손에는 **"우리 모임"**이라는 서비스가 남습니다. 동네 독서 모임 "책 읽는 저녁"의 일정을 알리고, 참석 신청을 받고, 사진을 모으는 서비스입니다. 모든 데이터는 연습용 가상 데이터입니다.

| 단계 | 회차 | 결과물 |
| --- | --- | --- |
| 시작하기 | 1–3회 | 요즘 흐름 이해, 기획서와 목업, 첫 웹페이지 |
| 웹앱 만들기 | 4–6회 | 내 PC의 웹앱 → 저장(Git) → 인터넷 주소로 공개 |
| 데이터와 로그인 | 7–9회 | 데이터베이스, 회원가입, 참석 신청·사진·검색 |
| AI 기능 | 10회 | 후기 요약, 안내문 초안을 쓰는 AI |
| 앱으로 | 11–14회 | 홈 화면 설치, 휴대폰 앱, 출시 준비 |
| 마무리 | 15회 | 운영 방법, 발표, 다음 계획 |

<Analogy title="운전 배우기와 비슷합니다">
  자동차 엔진이 어떻게 돌아가는지 몰라도 운전은 배울 수 있습니다. 대신 신호를 지키고, 거울을 보고, 목적지를 정하는 것은 운전자의 몫이지요. 이 과정은 엔진(코드)을 외우는 수업이 아니라 <b>AI라는 차를 안전하게 운전하는 법</b>을 배우는 수업입니다.
</Analogy>

## 생성형 AI가 무엇인가요

### 말귀를 알아듣는 만능 조수

<Term id="gen-ai">생성형 AI</Term>는 글, 그림, 코드처럼 **새로운 결과물을 만들어 내는 AI**입니다. 그중 글을 읽고 쓰는 AI를 <Term id="llm">LLM</Term>(거대 언어 모델)이라고 부릅니다. 오늘부터 쓸 <Term id="claude">Claude</Term>도 LLM입니다.

- 엄청난 양의 글을 읽고 배워서, 다음에 올 말을 아주 잘 예측합니다.
- 그래서 질문에 답하고, 글을 고치고, 표를 만들고, **프로그램 코드까지** 씁니다.
- 사람처럼 "아는" 것이 아니라 "그럴듯하게 이어 쓰는" 것이라, 가끔 틀린 내용을 자신 있게 말합니다. 이것을 <Term id="hallucination">환각</Term>이라고 합니다.

| AI가 특히 잘하는 일 | 사람이 꼭 확인해야 하는 일 |
| --- | --- |
| 글 요약, 정리, 다듬기 | 날짜, 금액, 이름 같은 사실 |
| 표와 목록 만들기 | 최신 소식 (AI가 배운 시점 이후의 일) |
| 아이디어 내기, 질문하기 | 법, 의료, 돈과 관련된 판단 |
| 코드 쓰기와 고치기 | 개인정보, 보안 |

<Analogy title="아주 똑똑한 신입 사원">
  AI는 책을 수만 권 읽은 신입 사원과 같습니다. 무엇이든 빠르게 해 내지만, 우리 모임의 사정은 모르고 가끔 아는 척도 합니다. 그래서 <b>상황을 자세히 알려 주고, 결과를 확인</b>하는 선배의 역할이 필요합니다.
</Analogy>

## 바이브 코딩의 탄생

2025년 2월 2일, OpenAI 공동창업자 **안드레이 카파시**가 X(옛 트위터)에 새로운 코딩 방식을 소개했습니다. 코드가 있다는 사실조차 잊고 분위기(vibe)에 몸을 맡겨 AI에게 말로 만들게 하는 방식, **<Term id="vibe-coding">바이브 코딩</Term>**입니다 ([원문](https://x.com/karpathy/status/1886192184808149383)).

이 말은 그해 콜린스 사전이 뽑은 **2025년 올해의 단어**가 됐습니다 ([Wikipedia](https://en.wikipedia.org/wiki/Vibe_coding)). 개발자들만의 유행어가 아니라, 사회 전체가 주목하는 변화가 된 것입니다.

### 무엇이 달라졌나

| 예전 | 지금 |
| --- | --- |
| 프로그램을 만들려면 몇 년 동안 코딩을 배워야 했다 | 말로 설명하면 AI가 코드를 쓴다 |
| 작은 아이디어는 "개발자에게 맡기기엔 너무 작아서" 포기했다 | 몇 분 만에 직접 만들어 써 볼 수 있다 |
| 만드는 사람과 쓰는 사람이 달랐다 | **문제를 가장 잘 아는 사람이 직접 만든다** |

<Analogy title="사진의 역사와 닮았습니다">
  예전에는 사진을 찍으려면 사진관에 가야 했습니다. 지금은 누구나 휴대폰으로 찍지요. 그렇다고 사진가가 사라지지는 않았습니다. 대신 <b>무엇을 찍을지 아는 사람</b>이 좋은 사진을 남깁니다. 소프트웨어도 같은 길을 걷고 있습니다.
</Analogy>

### 그런데 "알아서 해줘"만으로는 사고가 난다

바이브 코딩이 널리 퍼지면서 실제 사고도 생겼습니다.

| 시기 | 일어난 일 | 교훈 |
| --- | --- | --- |
| 2025년 | 한 바이브 코딩 플랫폼으로 만든 웹앱 1,645개 중 170개에서 개인정보가 새어 나갈 수 있는 취약점 발견 | 만든 뒤 **보안 점검**을 건너뛰면 안 된다 |
| 2025년 7월 | 한 AI 코딩 서비스가 "바꾸지 말라"는 지시에도 사용자의 운영 데이터베이스를 지움 | AI에게 **되돌릴 수 없는 권한**을 함부로 주면 안 된다 |

출처: [Wikipedia — Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding)

만드는 것은 AI가 해도, **무엇을 만들지 정하고 결과를 확인하는 것은 사람의 몫**입니다. 이 과정이 15회나 되는 이유가 여기 있습니다. 만드는 법보다 **안전하게 확인하는 법**을 함께 배우기 때문입니다.

## 에이전틱 엔지니어링

카파시는 2026년 4월 세콰이아 캐피털의 행사(Ascent)에서 이렇게 정리했습니다. "바이브 코딩은 바닥을 올리고, 에이전틱 엔지니어링은 천장을 올린다" ([요약 기사](https://www.aibuilderclub.com/blog/karpathy-agentic-engineering)). 누구나 시작할 수 있게 된 것이 바이브 코딩이라면, 제대로 된 서비스까지 가는 길이 에이전틱 엔지니어링이라는 뜻입니다.

**<Term id="agentic-engineering">에이전틱 엔지니어링</Term>**은 AI <Term id="agent">에이전트</Term>가 계획하고, 만들고, 시험해 보고, 사람은 **요구사항을 정하고 → 계획을 검토하고 → 결과를 검증**하는 일하는 방식입니다.

| 구분 | 바이브 코딩 | 에이전틱 엔지니어링 |
| --- | --- | --- |
| 말투 | "알아서 해줘" | "이렇게 해줘. 그리고 내가 확인할게" |
| 시작 | 바로 만들기 | 계획 먼저 보기 |
| 안전장치 | 거의 없음 | 되돌리기, 저장 기록(Git), 권한 승인, 점검 |
| 어울리는 일 | 나만 쓰는 연습용 | 다른 사람이 쓰는 서비스, 앱 출시 |

<Analogy title="집 짓기로 비유하면">
  바이브 코딩은 "예쁜 집 하나 지어 줘"라고 말하고 기다리는 것입니다. 에이전틱 엔지니어링은 건축주가 되는 것입니다. 설계도를 함께 보고, 공사 중간중간 현장을 확인하고, 다 지은 뒤 수도와 전기를 직접 틀어 봅니다. 벽돌은 AI가 쌓지만 <b>집주인은 여러분</b>입니다.
</Analogy>

1–3회는 가볍게 바이브 코딩으로 감을 익히고, 4회부터는 에이전틱 엔지니어링의 안전장치를 하나씩 더해 갑니다.

## 챗봇과 에이전트는 무엇이 다른가

### 상담원과 담당자

같은 Claude라도 쓰는 방식이 두 가지입니다.

| | 채팅 (Claude 웹·앱) | 에이전트 (<Term id="claude-code">Claude Code</Term>) |
| --- | --- | --- |
| 하는 일 | 대답하고, 글과 그림을 만들어 보여 준다 | **내 컴퓨터 폴더를 직접 열어** 파일을 읽고, 만들고, 고친다 |
| 결과 | 화면에 나온 답을 내가 복사해 저장 | 파일이 실제로 내 컴퓨터에 생긴다 |
| 실행 | 내가 직접 해 봐야 한다 | 프로그램을 실행해 보고 결과를 확인한다 |
| 틀렸을 때 | 내가 다시 질문 | 스스로 고쳐 보고 다시 확인 |
| 사람의 역할 | 손발 | **지시하고 승인하는 사람** |

<Analogy title="전화 상담원과 방문 기사님">
  채팅은 전화 상담원입니다. "이렇게 해 보세요"라고 친절히 알려 주지만 실제로 하는 것은 나입니다. 에이전트는 집에 방문한 기사님입니다. 직접 살펴보고, 고치고, 잘 되는지 틀어 보고 갑니다. 단, 중요한 것을 바꿀 때는 "이거 바꿔도 될까요?" 하고 묻습니다.
</Analogy>

### 권한 승인은 결재 버튼

Claude Code는 파일을 고치거나 프로그램을 실행하기 전에 **허락을 구합니다.** 이 승인 창이 우리의 첫 번째 안전장치입니다.

- 무엇을 하려는지 **읽고** 누르세요. 모르면 "이게 무슨 뜻이야?"라고 물어도 됩니다.
- 처음에는 하나하나 승인하는 것이 좋습니다. 익숙해지면 믿을 만한 일만 자동으로 허락할 수 있습니다.
- 실습은 항상 **연습용 폴더** 안에서 합니다. 그 폴더 밖의 파일은 건드리지 않습니다.

## 왜 Claude와 Claude Code로 배우나요

한 문장으로 답하면 이렇습니다. **생각을 정리하는 대화와 프로그램을 만드는 일이 끊기지 않고, 그 두 가지를 모두 최상위 수준으로 해내는 도구**이기 때문입니다.

### 기획과 개발이 한 사람, 한 대화 안에서

- **예전:** 기획하는 사람이 문서로 설명 → 개발자가 해석 → 생각과 다른 결과 → 다시 수정. 말이 옮겨질 때마다 뜻이 조금씩 새어 나갑니다.
- **지금:** 문제를 가장 잘 아는 사람이 직접 만들고, 써 보면서 바로 고칩니다. **기획서가 곧 설계도**가 됩니다.

| 순서 | 내가 하는 말 (예) | 쓰는 곳 | 남는 것 |
| --- | --- | --- | --- |
| 1 | "모임 참석 인원을 세는 게 너무 번거로워. 같이 생각해 보자" | 채팅 | 정리된 생각 |
| 2 | "질문해서 기획서로 정리해줘" | 채팅 | 기획서 |
| 3 | "기획서대로 화면을 그려줘" | 채팅(아티팩트) | 눌러 볼 수 있는 목업 |
| 4 | "이 목업대로 웹앱을 만들어줘" | Claude Code | 동작하는 웹앱 |
| 5 | "직접 실행해 보고 기획서대로 됐는지 표로 보여줘" | Claude Code | 점검표 |
| 6 | "알림 기능도 넣자. 기획서도 같이 고쳐줘" | Claude Code | 고쳐진 기획서와 웹앱 |

이 과정 전체가 이 흐름을 연습합니다. 2회는 1–3번, 3–10회는 4–6번을 웹·데이터·AI로 넓히고, 11–14회는 같은 흐름을 휴대폰 앱으로 옮깁니다.

### 다른 도구와 무엇이 다른가

AI 도구는 크게 네 종류입니다. 모두 좋은 도구이고 기능이 빠르게 늘고 있어서, 아래 표는 2026년 10월 기준의 **일반적인 특징**입니다.

| 구분 | 웹 채팅 (ChatGPT, Gemini, Claude 등) | 앱 빌더 (Lovable, Replit, Bolt 등) | 개발자 편집기 (Cursor, GitHub Copilot 등) | **Claude Code** |
| --- | --- | --- | --- | --- |
| 주로 쓰는 사람 | 누구나 | 웹앱을 빨리 만들려는 사람 | 개발자 | **처음 배우는 사람부터 개발자까지** |
| 내 컴퓨터 파일 | 올린 파일만 | 주로 그 서비스 안에서 | 코드 폴더 중심 | **폴더 전체를 직접** |
| 기획 문서 | 잘함 (복사해서 저장) | 앱 설명 위주 | 코드 중심 | **잘함, 파일로 바로 저장** |
| 코드 작성·실행·확인 | 코드만 보여 줌 | 웹앱 위주로 잘함 | 잘함 | **잘함, 직접 실행하고 확인** |
| 휴대폰 앱까지 | 어려움 | 일부 지원 | 가능 | **가능 (12–14회)** |
| 시작하기 | 가장 쉬움 | 쉬움 | 개발 지식 필요 | 쉬움 (데스크톱 앱) |

같은 종류(내 컴퓨터에서 일하는 에이전트)의 도구로는 OpenAI Codex, Google Gemini CLI 등도 있습니다. 개념은 같으니, 이 과정에서 익힌 **일하는 방식**은 다른 도구에서도 그대로 통합니다.

### 기획 문서도, 코드도 최상위 성능

이 과정의 핵심은 **같은 AI가 기획과 코드를 둘 다 잘해야** 한다는 점입니다. 기획서는 잘 쓰는데 코드가 약하거나, 코드는 잘 짜는데 설명이 어색하면 결국 둘 사이를 사람이 다시 번역해야 하기 때문입니다.

| 영역 | 근거 | 결과 |
| --- | --- | --- |
| **코드** | SWE-bench Verified — 실제 오픈소스 프로그램의 문제 500개를 고치게 하고 시험으로 채점하는 평가. 독립 평가 기관 Vals.ai 측정 | **Claude Opus 5가 97.0%로 1위** (2위 96.4%, 3위 96.2%, 2026-09-01 기준) |
| **글쓰기·대화** | Arena — 사람들이 두 AI의 답을 직접 비교해 투표하는 공개 순위 | 글쓰기·웹 개발 부문에서 Claude 모델이 꾸준히 최상위권 |
| **실제 사용** | Anthropic 안의 개발자가 아닌 부서 사례 | 법무팀·마케팅팀이 개발자 없이 업무 도구를 직접 제작 |

출처: [Vals.ai SWE-bench Verified](https://www.vals.ai/benchmarks/swebench), [Arena 순위](https://arena.ai/leaderboard), [How Anthropic teams use Claude Code](https://claude.com/blog/how-anthropic-teams-use-claude-code)

<Callout type="info" title="숫자보다 중요한 것">
  상위 모델끼리의 점수 차이는 1%p 안팎이고, 순위는 새 모델이 나올 때마다 바뀝니다. 이 과정이 Claude를 고른 이유는 점수 하나가 아니라, <b>최상위 수준의 글 능력과 코드 능력을 한 도구, 한 흐름 안에서 함께 쓸 수 있다</b>는 점입니다.
</Callout>

### 솔직한 한계

- Claude Code는 **유료(Pro 이상)** 플랜에서 쓸 수 있습니다: <Fact k="claude.plan" />
- 대화 내용은 AI 서비스로 **전송**됩니다. 실제 개인정보나 비밀은 넣지 않습니다.
- 결과는 언제나 **사람이 확인**해야 합니다. AI는 틀릴 수 있습니다.

## 요즘 업계에서는

### 개발자 대부분이 이미 AI를 쓴다

세계 최대 개발자 커뮤니티 Stack Overflow의 2025년 설문 결과입니다 ([2025 Developer Survey](https://survey.stackoverflow.co/2025/)).

| 질문 | 결과 |
| --- | --- |
| 개발에 AI 도구를 쓰고 있거나 쓸 계획인가 | **84%**가 "그렇다" |
| AI가 내놓은 답의 정확도를 믿지 않는다 | **46%** (전년 31%에서 증가) |
| 가장 답답한 점 | **66%**가 "거의 맞지만 완전히 맞지는 않은 답" |

흥미로운 점은 **많이 쓸수록 더 꼼꼼히 확인하게 된다**는 것입니다. 전문가들도 AI 결과를 그대로 믿지 않습니다. 이 과정에서 "확인하는 습관"을 계속 강조하는 이유입니다.

### 쓰고 버리는 소프트웨어

벤처캐피털 a16z는 2025년 8월 글에서, 그동안은 "만들 가치가 있나"를 따져서 소프트웨어를 만들었지만 이제는 만드는 비용이 거의 사라져 **상상력이 한계**가 됐다고 썼습니다 ([Disposable Software](https://a16z.com/disposable-software/)). 모임 출석부, 가족 장보기 목록처럼 "앱까지 만들 일은 아니던" 것들을 이제 직접 만들어 쓸 수 있습니다.

### 코드를 쓰는 AI에서 일을 끝내는 AI로

2024년까지 AI는 주로 "코드를 알려 주는" 역할이었습니다. 2025–2026년에는 직접 파일을 만들고, 실행하고, 시험하고, 고치는 **에이전트**가 중심이 됐습니다. 사람의 역할도 "코드를 치는 사람"에서 "무엇을 만들지 정하고 확인하는 사람"으로 옮겨 가고 있습니다.

<DeepDive title="그러면 개발자는 사라지나요?">
  그렇지 않습니다. 오히려 복잡한 서비스, 보안, 큰 시스템 설계처럼 깊은 지식이 필요한 일은 더 중요해졌습니다. 달라진 것은 <b>작은 소프트웨어를 만드는 문턱</b>이 아주 낮아졌다는 점입니다. 동네 가게 사장님, 모임 총무, 선생님처럼 문제를 가장 잘 아는 사람이 직접 작은 도구를 만들 수 있게 됐습니다. 그리고 그렇게 만든 것이 커지면, 그때 전문가와 함께 키우면 됩니다.
</DeepDive>
