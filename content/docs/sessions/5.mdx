## 왜 Git이 필요한가

### "최종_진짜최종_수정2.docx"의 비극

이런 파일 이름, 한 번쯤 만들어 보셨을 겁니다.

```
안내문.docx
안내문_최종.docx
안내문_최종_수정.docx
안내문_최종_진짜최종.docx
```

어느 것이 진짜 최신인지, 무엇이 바뀌었는지, 어제 버전으로 돌아가려면 어떻게 하는지 알 수 없습니다. 웹앱은 파일이 수십 개라 이 방식으로는 감당할 수 없습니다.

### Git: 게임의 세이브 포인트

<Term id="git">Git</Term>은 폴더의 **변경 기록을 저장하는 도구**입니다. 전 세계 개발자 대부분이 씁니다.

<Analogy title="게임의 세이브 포인트">
  어려운 보스를 만나기 전에 저장해 두면, 져도 그 자리에서 다시 시작할 수 있습니다. Git의 <b>커밋</b>이 바로 세이브입니다. 잘 돌아갈 때마다 저장해 두면, 무엇을 망쳐도 그때로 돌아갈 수 있습니다.
</Analogy>

3회에 배운 Claude Code의 되돌리기(<Kbd keys="esc" /> 두 번)는 **이번 대화 안에서만** 통하는 임시 되돌리기입니다. Git은 며칠, 몇 달 전으로도 돌아갈 수 있는 **튼튼한 기록**입니다.

| | Claude Code 되돌리기 | Git |
| --- | --- | --- |
| 얼마나 오래 | 주로 지금 대화 안 | 영원히 (지우지 않는 한) |
| 무엇을 | Claude Code가 고친 파일 | 폴더 전체 |
| 언제 저장 | 자동 | **내가 커밋할 때** |
| 다른 컴퓨터로 | 안 됨 | GitHub로 가능 |

### 꼭 알아야 할 말 네 개

| 말 | 뜻 | 게임으로 치면 |
| --- | --- | --- |
| <Term id="repository">저장소</Term> | Git이 기록을 남기는 폴더 | 세이브 파일이 있는 게임 |
| <Term id="commit">커밋</Term> | 지금 상태를 이름 붙여 저장 | 세이브 하나 ("보스 앞") |
| 커밋 이력 | 지금까지의 세이브 목록 | 세이브 슬롯 목록 |
| <Term id="push">푸시</Term> | 내 기록을 GitHub에 올리기 | 클라우드 세이브 |

아래 시뮬레이터에서 기능을 하나씩 더하며 커밋해 보고, 일부러 망친 뒤 이전 커밋으로 돌아가 보세요.

## GitHub: 클라우드 금고

### Git과 GitHub는 다르다

| | Git | <Term id="github">GitHub</Term> |
| --- | --- | --- |
| 무엇 | 기록을 남기는 **도구** | 기록을 올려 두는 **인터넷 서비스** |
| 어디에 | 내 컴퓨터 | 인터넷 (클라우드) |
| 비유 | 사진기 | 사진을 올려 두는 클라우드 앨범 |

<Analogy title="컴퓨터가 고장 나도">
  내 컴퓨터에만 세이브가 있으면, 컴퓨터가 고장 나는 순간 모두 사라집니다. GitHub에 올려 두면 다른 컴퓨터에서도 이어서 할 수 있습니다. 그리고 6회에는 <b>GitHub에 올린 것을 그대로 인터넷에 공개</b>합니다.
</Analogy>

### 공개와 비공개

GitHub 저장소는 **공개(public)** 또는 **비공개(private)**로 만들 수 있습니다.

| | 공개 | 비공개 |
| --- | --- | --- |
| 누가 보나 | 인터넷의 누구나 | 나와 내가 초대한 사람만 |
| 좋은 점 | 포트폴리오로 보여 줄 수 있다 | 마음 편히 연습할 수 있다 |
| 주의 | **비밀 키나 개인정보가 절대 들어가면 안 된다** | 그래도 비밀 키는 넣지 않는다 |

처음에는 **비공개**를 추천합니다. 나중에 언제든 공개로 바꿀 수 있습니다.

### 로그인은 언제나 내가 직접

GitHub에 올리려면 로그인이 필요합니다. 비밀번호나 인증 코드는 **언제나 본인이 직접** 입력합니다. Claude Code에게는 "방법만 알려줘, 로그인은 내가 할게"라고 하세요.

## 올리면 안 되는 것

### .gitignore: 금고에 넣지 않을 목록

폴더 안에는 GitHub에 올리면 안 되는 파일도 있습니다. 그 목록을 적어 두는 파일이 <Term id="gitignore">.gitignore</Term>입니다.

| 올리면 안 되는 것 | 왜 |
| --- | --- |
| `.env` 같은 비밀 파일 | 비밀번호, API 키가 들어 있다 (8회, 10회에 다룸) |
| 개인정보가 든 파일 | 회원 명단, 연락처 |
| `node_modules` 폴더 | Next.js 부품 수만 개. 언제든 다시 내려받을 수 있다 |
| 큰 사진·영상 | 저장소가 무거워진다 |

<Analogy title="이사할 때 짐 싸기">
  이사 갈 때 가스 밸브나 집 열쇠 사본을 상자에 넣어 택배로 보내지 않지요. .gitignore는 <b>"이건 택배로 보내지 마"</b> 목록입니다.
</Analogy>

### 한 번 올라간 비밀은 지워도 남는다

Git은 **모든 기록을 남기는** 도구라서, 비밀 키가 든 파일을 한 번 커밋해 올리면 나중에 지워도 **이전 기록에 그대로** 남습니다. 그래서 순서가 중요합니다.

1. 저장소를 만들 때 **.gitignore부터** 넣습니다.
2. 올리기 전에 **점검**합니다.
3. 실수로 올렸다면 **키를 새로 발급**합니다. 지우는 것만으로는 부족합니다.

## 요즘 업계에서는

### 1억 8천만 명이 쓰는 금고

GitHub의 Octoverse 2025 보고서에 따르면 GitHub에서 일하는 개발자는 **1억 8천만 명이 넘고**, 2025년 한 해 동안 **약 10억 번의 커밋**이 올라왔습니다. 평균 **1초에 한 명** 이상이 새로 가입했다고 합니다 ([Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)). 오늘 여러분도 그중 한 명이 됩니다.

### AI가 많이 만들수록 기록이 더 중요해진다

AI 에이전트는 몇 분 만에 파일 수십 개를 바꿉니다. 빠른 만큼 실수도 빠르게 퍼집니다. 그래서 요즘 AI로 개발하는 사람들은 **작게 바꾸고 자주 커밋**하는 습관을 가장 기본으로 꼽습니다. 2025년 7월 한 AI 코딩 서비스가 운영 데이터베이스를 지운 사건([Wikipedia — Vibe coding](https://en.wikipedia.org/wiki/Vibe_coding))도, 되돌릴 수 있는 기록이 얼마나 중요한지 보여 줍니다.

### 비밀 키 유출은 생각보다 흔하다

보안 회사 GitGuardian의 2025년 보고서에 따르면, 2024년 한 해 동안 공개 GitHub 저장소에서 **2,380만 건의 비밀 정보**(비밀번호, API 키 등)가 새어 나왔고, 2022년에 새어 나간 비밀의 **70%가 여전히 쓸 수 있는 상태**였습니다 ([The State of Secrets Sprawl 2025](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2025/)). 전문가들도 하는 실수입니다. 처음부터 .gitignore를 넣고, 올리기 전에 점검하는 습관이 가장 확실한 예방입니다.
